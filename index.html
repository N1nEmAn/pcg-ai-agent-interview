二、Web 漏洞：每题只背四句话

XSS｜数据变成浏览器代码
入口：用户输入 → HTML/属性/URL/JS/DOM sink。
证据：浏览器执行了攻击者控制的脚本。
修复：按输出上下文编码；安全模板/Sanitizer；CSP 只是兜底。
追问：为什么过滤不够？因为上下文不同，HTML 编码不能直接代替 JS/URL 编码。
SQL 注入｜数据变成 SQL 语法
入口：字符串拼接查询。证据：错误、布尔差异、时间差异或未授权数据。修复：参数化/预编译；动态表名、列名、排序字段用 allowlist。
追问：登录不等于授权，参数化也不解决对象级权限。
IDOR/BOLA｜登录了但不该看这个对象
入口：改 URL/JSON 中的对象 ID。证据：用户 A 读写用户 B 资源。修复：服务端每次做对象级授权，校验用户、租户、角色和资源状态。
换 UUID 只能降低枚举，不能替代授权。
SSRF｜让服务器替我访问网络
入口：URL/图片/网页抓取/导入功能。证据：服务端请求了目标并返回可观测结果。修复：出站 allowlist；解析后检查 IPv4/IPv6；阻断 loopback、私网、metadata；重定向逐跳检查；限制协议、响应、超时。
不能只做字符串黑名单，要防 DNS rebinding。
CSRF｜浏览器自动带 Cookie
修复：CSRF token + Origin/Referer + SameSite；状态变更不用 GET。
CORS 管跨源读取，不能单独防 CSRF。
上传/命令/路径穿越
上传：服务端检查内容、随机命名、Web 根目录外、禁止执行。命令：不用 shell，参数数组+allowlist。路径：规范化后确认仍在固定基目录，最好 ID 映射文件。

三、面试官高频追问｜点击展开

“怎样提高漏洞召回率？”

先固定授权靶场、漏洞实例标签、账号、预算和 verifier。把 FN 分桶：资产发现、认证态、参数覆盖、假设生成、工具执行、验证器、报告。优先改最大桶，一次只改一个环节做消融，并同时看 precision、重复、成本和延迟。增加轮次可能只增加重复和误报。

“Agent 已经打开网页，为什么仍会漏 API 漏洞？”

页面不等于完整攻击面：API 可能藏在 JS、OpenAPI、GraphQL、移动端接口、不同角色流程或未链接端点里。需要资产枚举、流量记录、schema/JS 分析和角色状态机，并把发现结果写入可查询状态。

“怎么判断是模型不会，还是 verifier 不行？”

记录逐 turn 轨迹：若没有提出假设，是 planner/覆盖问题；若提出且工具触发但判失败，是 verifier/证据问题；若已判定但报告丢失，是聚合/去重问题。对每层单独离线评估，不能只看最终报告。

“间接 Prompt Injection 怎么防？”

把网页/搜索结果标成不可信数据，与系统指令结构隔离；工具采用最小权限和 allowlist；敏感动作策略审批；凭据、会话和租户隔离；限制模型根据外部文本触发外发、改权限或访问内网。

“你的 Harness 哪些是真的？”

只说能拿出代码和日志证明的部分。区分已实现、跑通过 demo、设计计划。准备工具 schema、轨迹字段、reset/replay、样本量、失败案例和排名依据，不要用“理解了”替代工程证据。

“SOFT 项目和岗位有什么关系？”

它证明我会做可信评估：数据标记污染会制造虚高 AUC，必须做数据质检、独立复算和多攻击验证。迁移到 Agent，就是先保证漏洞标签和 benchmark 可信，再讨论召回提升。它不是 Web 渗透 Agent 生产结果。

09 · FOUNDATIONHTTP、认证和浏览器安全：面试官默认你应该会

一次请求的安全观察点

方法：GET 通常读取，POST/PUT/PATCH/DELETE 可能改变状态；不能只靠方法名判断安全性。
路径与参数：路径参数、查询参数、JSON、表单、Header、Cookie 都可能是输入。
身份：Cookie、Authorization、客户端证书、API key。
来源：Origin、Referer、Host、重定向链和代理头都可能影响信任判断。

状态码不要死记

2xx 表示处理成功，不代表权限正确；3xx 可能引入重定向和 SSRF 风险；4xx 可能暴露对象是否存在；5xx 可能泄露堆栈或内部服务信息。比较安全性时同时看状态码、响应长度、Header、时间、Body 和后续状态变化。

Cookie 属性

HttpOnly 限制脚本读取 Cookie，不能阻止浏览器自动携带；Secure 要求 HTTPS；SameSite 限制跨站携带；Domain/Path/Max-Age 决定作用范围和生命周期。它们降低风险，但不替代服务端授权。

JWT 高频坑

验证签名算法、密钥、exp、nbf、iss、aud 和 token 撤销策略；不要信任客户端传来的角色字段；不要把“JWT 没被改”误当成“访问一定被授权”。

同源策略、CORS、CSRF 的一张表

概念主要保护什么常见误解面试一句话
同源策略浏览器脚本读取其他源资源以为服务器之间不能互相请求它是浏览器的读取隔离边界
CORS服务端声明哪些跨源读取可被浏览器放行以为开启 CORS 就能防 CSRF它管跨源读取，不自动阻止状态改变请求
CSRF防止跨站利用受害者凭据改变状态以为攻击者必须能读响应重点是自动携带凭据和有副作用的请求
“为什么错误信息、响应长度和时间也算证据？”

安全验证不只看 HTTP 状态码。布尔盲注、对象存在性泄露、权限差异、SSRF 到 canary 服务等场景可能只表现为长度、Header、延迟或后续状态变化。证据要提前定义，并通过重复请求、对照请求和独立日志降低偶然性。

10 · DEEP DIVE少见但可能被追问的漏洞

业务逻辑与竞态

原理：每个接口单独看似安全，但步骤顺序、状态转换、并发请求或金额/库存检查组合后可绕过业务规则。
验证：用两个角色和两个并发请求检查“检查—使用”之间的窗口。
修复：服务端状态机、事务、幂等键、行锁/版本号、重放检测。
回归：重复提交、并发下单、权限变更中操作和失败重试。

开放重定向

原理：跳转参数允许任意外部地址，可能被用于钓鱼、OAuth code 泄露或 SSRF 链。
修复：相对路径或固定 allowlist，解析后校验 scheme/host，禁止混淆编码。
回归：协议相对 URL、用户名密码、双重编码、多个重定向。

缓存投毒/缓存错配

原理：缓存键没有包含影响响应的 Header/参数，攻击者让共享缓存存入恶意响应。
修复：明确缓存键和 Vary，私有内容不进共享缓存，规范化 Host/路径。
回归：不同用户、Header、查询参数和错误响应交叉请求。

敏感信息泄露

原理：日志、错误堆栈、前端 bundle、备份文件、配置或响应字段暴露密钥和内部数据。
修复：最小回显、密钥托管和轮换、日志脱敏、构建产物检查、权限隔离。
回归：错误路径、调试开关、压缩包、旧版本和不同角色。

SAST / DAST / IAST：和 AI Agent 的关系

方法看什么优点局限Agent 可补什么
SAST源码、数据流、调用图早期、覆盖代码路径可能不理解真实配置/业务状态，误报多理解上下文、生成验证请求、解释修复
DAST运行中的黑盒行为接近真实攻击面发现不了未覆盖端点，状态/登录难规划探索、角色切换、参数和流程覆盖
IAST运行时插桩和代码路径能把请求和代码 sink 关联需要部署插桩，环境成本高结合证据排序和生成回归用例

合理方向不是让 Agent 取代所有扫描器，而是让确定性工具提供信号，Agent 负责自适应探索、假设生成、证据整合和可解释报告。

11 · AGENT ENGINEERING把 Harness 说到工程细节

一次 turn 的可观测协议

{ "trace_id": "run-17-turn-08", "scope": {"host": "lab.local", "allowed_methods": ["GET","POST"]}, "observation": {"url": "/orders/1001", "role": "user_A", "known_assets": 23}, "action": {"tool": "http_request", "args": {"method": "GET", "path": "/api/orders/1002"}}, "policy_decision": {"allowed": true, "reason": "same authorized lab"}, "tool_result": {"status": 200, "body_hash": "...", "latency_ms": 84}, "verify": {"candidate": "BOLA", "evidence_level": "strong"}, "termination": null }

关键是每个动作可以回放、审计和归因。不要只保存最终文本；至少保存观察、动作、工具原始结果、归一化结果、策略判断、验证结论和预算。

状态应该结构化

建议字段：scope、identities、assets、endpoints、parameters、hypotheses、evidence、budget、trace_id。每条事实带来源、时间和置信度，避免把模型猜测写成事实。

工具 schema 不是装饰

定义必填字段、类型、枚举、长度和目标范围；服务端再次校验，不能相信模型生成的 JSON。设置超时、重试上限、并发限制、幂等键和危险动作策略。工具错误要结构化返回，让模型能恢复。

失败恢复

区分网络超时、参数校验失败、权限拒绝、目标不存在、响应太大和工具崩溃。指数退避只适合临时错误；参数错误应修正或终止；连续失败要回滚/换工具，而不是盲目重试。

终止条件

成功证据、预算耗尽、重复动作、超出 scope、检测到破坏性风险、连续工具失败和需要人工批准，都应该成为明确的 termination reason。

一个安全的 Agent loop 应该是什么样？

observe → plan（结构化 JSON）→ policy/schema validate → execute tool → normalize result → independent verify → update state → evidence/dedupe/report。模型提出的“我要访问某地址”不等于允许访问；策略层、网络层和凭据层都要再次判断。

如何安全证明 SSRF，而不碰真实内网？

只在明确授权的实验环境里使用 canary 服务：让目标服务访问一个你控制的、只记录 request-id 的 URL，观察 canary 日志和响应是否回流。用本地 mock 的 redirect、DNS 变化和私网模拟器测试解析逻辑；不要访问真实云 metadata、公司内网或第三方系统。证明原语即可，不需要读取敏感数据。

12 · BENCHMARK DESIGN漏洞召回率：从公式到可复现实验

先定义一个漏洞实例

一种可操作的唯一键是：(asset, endpoint, vuln_type, parameter, auth_context)。例如同一个 API 的“普通用户读他人订单”和“管理员导出他人订单”可以是不同权限上下文。预先写清 strict/lenient 匹配规则，否则同一漏洞多次报告会虚增指标。

Ground truth 怎么来

使用人工确认的授权靶场、种植的测试漏洞、代码/配置审计和独立 verifier。训练题和测试题按应用、端点或漏洞实例隔离，避免相似流程泄漏。每个实例存前置身份、触发步骤、证据阈值、修复版本。

指标要分层

Instance-level：最终交付的漏洞是否正确。
Step-level：是否发现端点、拿到身份、触发工具或提出假设。
报告微平均和宏平均 recall；多次随机运行报告均值、方差或置信区间。

成本不能漏

每题 Token、HTTP 请求、工具调用、墙钟时间、p95 延迟、失败率、重复报告和人工审核量。真实岗位通常要在覆盖、准确、速度和预算之间做取舍。

FN 分桶与改进实验

漏检桶可观察信号对应改进
Discovery资产图缺少 API/JS/隐藏端点流量记录、schema/JS 分析、路径枚举
Auth/State只在一个角色或错误步骤执行角色状态机、会话刷新、前置条件检查
Coverage没有触达关键参数/业务流程参数生成、状态覆盖、跨步骤记忆
Hypothesis已有输入和 sink，但未提出漏洞假设类型化 checklist、检索记忆、任务分解
Toolschema 错、超时、重试耗尽工具校验、错误恢复、资源预算
Verifier已有触发证据却报告为无漏洞规则/差分/日志证据和独立 verifier
Report已判定但去重/聚合后丢失稳定漏洞 ID、证据存档和报告回归

13 · ANSWER TEMPLATES30 秒和 3 分钟两种回答长度

30 秒：怎样提高召回率？

我会先固定授权靶场、漏洞实例粒度和 ground truth，用 TP/(TP+FN) 计算 recall。然后把漏检按资产发现、登录态、参数覆盖、假设生成、工具执行、verifier 和报告分桶，针对最大桶一次改一个环节做消融，同时看 precision、重复、成本和延迟。这样能知道是哪里变好了，而不是笼统增加扫描轮次。

3 分钟：怎样提高召回率？

第一步定义实例唯一键和证据阈值，隔离训练/测试应用。第二步让 trajectory 记录每个 turn 的观察、动作、工具结果、策略判定和 verifier 结论。第三步跑固定预算 baseline，生成 FN 桶。第四步只改变一个环节，例如 API 发现或角色状态机，配对比较微/宏平均 recall、precision、重复、Token 和 p95 延迟。最后对困难样本和未见应用做 held-out 验证，防止 benchmark 过拟合。

30 秒：为什么适合这个岗位？

我有传统安全里的攻击面、权限和证据意识，也在做模型、Agent 工具调用和 Harness。岗位要优化召回率，本质是把“模型有没有想到”拆成发现、状态、执行、验证和报告几个可观察环节，我能用安全经验判断漏洞，也能用实验方法定位漏检。

被问“没有 recall 提升指标怎么办？”

不虚构结果。可以说目前已有排名、漏洞复现和评估经验，但还没有完成生产级 Agent 的 recall 对照；我会先建立小型授权 benchmark，固定 ground truth、预算和 verifier，再给出可复算的 baseline 与改进结果。能清楚说出实验设计和限制，比编造百分比更可信。

14 · PRACTICE今晚可以口述的练习题

练习 A：XSS 修复验收

练习 C：Agent 漏检定位

Agent 已登录但没报出 IDOR。检查资产图、角色状态、对象 ID 覆盖、请求是否真的发出、响应差分、verifier 和报告去重，给每一步一个日志字段。

练习 D：安全证明 SSRF

设计一个本地 canary URL 和 mock redirect；记录 request-id、解析 IP、重定向跳数、响应大小和策略决策。说明为什么不需要访问真实内网就能证明请求原语。
