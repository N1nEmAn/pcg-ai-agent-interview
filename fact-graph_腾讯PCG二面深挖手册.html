02 · PROJECT MODEL先把项目画成一张图

一口气说清楚

fgc 把 Agent 工作拆成两类节点：已确认的 fact 和待完成的 intent。fact 是图上的节点，intent 是依赖若干事实、产出新事实的工作边。所有状态落在项目目录的 .fg/ 中，Claude Code 的 hook 每轮注入压缩后的图状态，调度器通过 prompt 驱动 reason、explore 和 verify。

事实和工作分离

“服务器返回 200”是观察事实；“验证对象级授权”是 intent。把猜测、正在做的事和已确认结果分开，后续 Agent 才不会把假设当结论，也能从中断处继续。

03 · DATA MODELfact / intent / frontier：面试官会问到字段级

对象在项目里的含义面试要点
fact已确认的观察或可复现结果，写入后不可变防止 Agent 把猜测覆盖成事实；详细证据放 doc，需要时用 fgc doc 读取
intent一个工作单元，from 是依赖事实，to 是产出事实状态由图结构表达：open/claimed/done/confirmation；依赖满足后进入 frontier
hint给 commander 的人类留言不混入事实，防止临时建议被误当已验证结果
frontier当前依赖已满足、可执行的 intent 集合可以并行调度，但要处理 claim、超时和重复完成
一个容易被问的点：fact graph 的“图”不靠图数据库实现，而是每个节点一个 JSON 文件，intent 的 from/to 形成 DAG。这样可读、可 diff、易恢复；当节点数量和查询复杂度增长时，SQLite 或专门索引会更合适。

04 · ENGINEERING DEEP DIVE代码层面最可能的追问

Q1 · 两个 Agent 同时完成同一个 intent，怎么避免重复？ P0

面试官想听：不是一句“加锁”，而是锁住什么、何时再次检查、失败后留下什么。

你的回答：Store 的写入通过项目级 lock 文件和 fcntl.flock 串行化。执行器完成任务后进入同一临界区，再读取 intent 检查 to 是否已经存在；只有仍然开放时才分配事实 ID、写事实并回写 intent。这样第二个执行器会发现 intent 已结束并丢弃重复结果。代码里的 conclude_with_new_fact 还把 fact 写入和 intent 关联放在同一个应用级锁中。
边界：这保证了本地多进程并发下的互斥和重复检查，不等于跨机器分布式锁，也不是数据库级崩溃事务。

Q2 · 原子写入解决什么？ P0

你的回答：先把 JSON 写到同目录临时文件，再用 os.replace 替换目标文件，避免读者看到半截 JSON；fcntl 保护同一项目的并发写入。它解决文件级可见性和写入竞争，不能自动保证多个文件跨崩溃的一致提交。

Q3 · 如果进程写完 fact 后就在回写 intent 前崩溃呢？ P0

高质量回答：当前设计在同一个锁里执行，能防并发交错；但文件系统没有跨文件事务，理论上仍要考虑事实已落盘而 intent 未链接的孤儿节点。可以用启动时一致性检查、事务日志/commit marker、写入顺序和恢复扫描解决。面试时不要把应用级锁说成完整数据库事务。

Q4 · 为什么不用 SQLite 或 Redis？ P0

你的回答：当前目标是在 Claude Code 项目内部提供轻量、可 diff、零依赖、可恢复的工作记忆，JSON 文件更容易人工检查和随项目移动。SQLite 更适合复杂查询、事务和大量节点；Redis 适合共享服务和低延迟，但引入了服务和生命周期。项目规模上来后可以把存储抽象成接口，再换 SQLite/Postgres，保留 fact/intent 语义。

Q5 · recall 是向量检索吗？ P1

准确回答：当前 fgc recall 是轻量文本相似度：分词重叠加 difflib 兜底，不是 embedding 向量数据库。它适合少量本地事实的快速复用；大量节点、语义改写或跨项目检索时，需要倒排索引、embedding 或混合检索，并保留来源和置信度。

Q6 · 当前 verify 真的是独立验证器吗？ P0

准确回答：仓库有 dispatch verify 和 verify.md，它会读取 intent 和产出 fact，再调用 Claude 判断 verified/issues；但目前主要是对结果做二次审阅，并不会自动重新执行漏洞请求，也没有把验证状态完整写回事实图。因此它是核验流程的原型，不应包装成独立安全 verifier。

改进方向：为安全任务增加结构化证据、可复现请求、差分响应、canary 日志、规则检查和独立状态字段，让 verifier 能输出 confirmed / inconclusive / rejected。

05 · SECURITY BOUNDARY面试官会把你的 Agent 往攻击面上推

图里的内容可信吗？

不自动可信。fact 可能来自代码、网页、工具输出或之前的 Agent；模板把 graph block 标成 untrusted data，要求模型把其中的“运行命令”当观察内容。这个是提示层防护，不能替代沙箱、文件权限和网络隔离。

--skip-permissions 的风险

如果不可信仓库里的 .fg/*.json 被拼入 prompt，同时 executor 拥有 shell 权限并跳过确认，恶意事实可能诱导 Agent 执行命令。运行 autonomous mode 前要确认 graph 来源、scope 和权限。

peer 通信为什么要授权

fgc peers --discover 只列出 tmux pane；只有用户用 peers --add 明确授权后，send/capture 才能访问目标。配置在项目本地 .fg/ai-peers.json，消息记录到 channel 文件。

凭据和租户隔离

图里应保存凭据引用和角色上下文，避免把 token 原文写入 fact；工具层按 scope、身份和目标 allowlist 做二次检查；跨租户事实、会话和报告要隔离。

如果面试官问：为什么把外部文本标为不可信还不够？

因为模型可能仍然被诱导，文本防护没有阻止工具访问内网、读取文件或外发数据。真正的安全边界应在策略层、工具 schema、网络 egress、进程沙箱、凭据托管和人工审批中。Prompt 只负责告诉模型如何解释数据，不能赋予或撤销操作权限。

06 · MIGRATE TO PENTEST怎样把 fact-graph 迁移到智能渗透 Agent

scope / 目标→资产 fact→身份/状态 fact→漏洞 hypothesis intent→工具执行→证据 fact→verifier / report
fact-graph 概念渗透 Agent 对应物注意点
fact已发现端点、角色、响应差异、canary request-id、代码 sink只写确认结果；推测放 hypothesis，不要污染事实
intent枚举 JS API、用 A/B 角色验证对象权限、验证 SSRF canary每个 intent 有范围、成功证据、预算和终止条件
frontier当前满足前置条件、可执行的测试任务按风险和信息增益排序，避免重复探索
doc请求/响应、日志、复现步骤和修复建议正文摘要进入上下文，细节按需读取
迁移时要补的东西：通用 fact graph 只负责记忆和任务依赖；渗透场景还需要 scope enforcement、凭据隔离、危险命令策略、结构化漏洞 schema、独立 verifier、证据等级和 recall/precision benchmark。

07 · EVALUATION二面可能追问：你怎么证明系统真的变好了

漏洞实例

用 (asset, endpoint, vuln_type, parameter, auth_context) 唯一化；预先规定 strict/lenient matching，避免同一漏洞重复报告。

指标

Recall = TP/(TP+FN)；同时看 precision、F1、重复率、Token/请求数、p95 延迟、人工审核量和高风险漏洞覆盖。

漏检分桶

Discovery、Auth/State、Coverage、Hypothesis、Tool、Verifier、Report。每次只改一个最大桶，做 baseline、配对消融和 held-out 应用验证。

run_id: same benchmark + same accounts + same seed budget: max_turns / requests / tokens / timeout trace: observation → action → tool_result → verify → report compare: baseline vs one changed component report: recall, precision, duplicates, cost, p95 latency, failure buckets

回答岗位问题时，可以把 fact-graph 作为“让 Agent 记住并复用已确认事实、减少重复探索”的基础设施；召回率提升仍要靠独立 benchmark 和 verifier 证据证明。

08 · QUESTION CARDS二面高频问题：先自己回答，再展开模板

Q1：为什么做 fact-graph？普通聊天记录不够吗？

答：聊天记录是线性、难查询、容易把假设和事实混在一起；fact-graph 用不可变 fact、带依赖的 intent 和 frontier 表达“确认了什么、下一步能做什么”，可以跨轮次恢复、减少重复探索，并让人用 git diff 检查。规模增大后再考虑 SQLite 或向量检索。

Q2：fact 为什么不可变？如果发现事实错了怎么办？

答：不可变保证历史可追溯，纠错时新增一个“旧事实被反证/修正”的 fact，并让后续 intent 依赖新事实；也可以给事实加 provenance、置信度和废弃标记，但不直接覆盖历史。

Q3：DAG 如何保证没有循环？

答：当前 intent 只引用已经存在的 fact，intent 完成后产出新 fact，正常写入路径天然向前；如果开放原始编辑或导入数据，仍要做依赖检查、拓扑校验和异常图检测，不能只依靠命令约定。

Q4：文件锁在多 Agent 场景下有什么局限？

答：fcntl 适合同一台 POSIX 主机上的并发进程；NFS、容器跨节点、Windows 或网络分布式环境需要不同的锁服务或数据库事务。还要处理 stale claim、worker 崩溃、租约和重试。

Q5：你怎样处理 Agent 写入的恶意事实？

答：来源标记、事实 schema、工具结果与模型解释分层、prompt 中明确 untrusted data；执行时仍用 scope、策略、沙箱、网络隔离和权限校验。文本围栏是提醒，不是安全边界。

Q6：主 Agent 和 Worker Agent 为什么这样分工？

答：主 Agent 保持全局目标、优先级和依赖；Worker 处理窄任务，减少上下文污染和重复推理。共享图让 Worker 交付结构化事实，主 Agent 从 frontier 继续调度。需要防止共享事实冲突、过期和错误传播。

Q7：如果让你把 fgc 用于 IDOR 验证，怎么建图？

答：先记录 scope、应用、两个身份和自己的对象作为事实；创建“替换对象 ID”的 intent；工具结果记录响应差异和状态变化；确认后写入 BOLA evidence fact；再由 verifier intent 复现并输出 confirmed/inconclusive/rejected；报告节点引用证据而不是只引用模型判断。

Q8：当前项目最需要改进什么？

答：第一是把 verify 从结果审阅升级成真正可复现的独立验证器并持久化 verdict；第二是给 intent 加租约和恢复策略；第三是补 schema/provenance/confidence 和一致性检查；第四是用授权靶场做 recall、precision、成本和延迟 benchmark；规模化后再抽象存储层。

Q9：你如何证明 fact-graph 减少了重复探索？

答：当前如果没有严格对照，就不报告提升百分比。可以固定任务集和预算，比较无图、线性历史、fact-graph 三个版本，统计重复工具调用、重复假设、完成率、Token、延迟和成功证据数，再做多次运行和困难任务 held-out。

Q10：这个项目和岗位的关系是什么？

答：岗位要优化智能渗透 Agent 的覆盖和验证质量，fact-graph 提供了持久状态、任务依赖、经验复用和多 Agent 协作基础；我还需要把通用图扩展为安全 schema、权限边界、独立 verifier 和漏洞评测，才能形成岗位所需的生产闭环。

Q11：如果面试官让你现场写一个 ready frontier，怎么思考？

答：读取所有 open intent，过滤 requires_confirmation 未确认、已有 worker 租约的节点，再检查 from 中每个 fact 是否存在；按优先级/信息增益排序。并发领取时要在锁内重新检查并写入 worker，避免两个 worker 同时拿到同一个 intent。

Q12：为什么 verify 不能只看模型 confidence？

答：confidence 是模型自评，可能只是语言流畅。验证器要结合可重复请求、差分响应、状态变化、canary 日志、代码 sink 或规则，证据不足时返回 inconclusive，并进入下一步测试或人工复核。

09 · SPEAKING TEMPLATES直接练这三段

30 秒项目介绍

我做了一个叫 fact-graph 的工作记忆工具 fgc，运行在 Claude Code 项目内部。它把已确认事实建成不可变节点，把待完成工作建成依赖事实的 intent，通过项目本地的 JSON 图保存状态，并用 hook、reason、explore、verify 让 Agent 可以恢复工作、减少重复探索。它是轻量的本地原型，当前 verify 还不是完整的独立安全验证器，下一步会加入结构化证据、权限边界和 benchmark。

90 秒工程细节

存储层每个 fact 和 intent 一个 JSON 文件，project.json 保存目标和计数器；写入用临时文件加 os.replace，项目内并发用 fcntl flock。intent 的 from 指向依赖事实，to 指向产出事实，frontier 是依赖满足且可执行的工作。dispatch 通过 reason、explore、verify 模板调用 Claude CLI，执行结果解析后写回图。并发完成时，在锁内重新检查 intent 是否已有 to，避免重复事实。它的边界是本地 POSIX 并发和应用级一致性，跨节点、崩溃事务、独立 verifier 和指标评测还需要继续补。

被问“你有什么不足”

我目前最需要补的是生产级安全验证和可量化效果。我已经把 Agent 工作拆成状态、工具、事实和任务依赖，但当前 fgc 的 verify 主要是对执行结果做二次审阅，还没有自动复现请求并持久化独立 verdict。下一步我会在授权靶场建立 ground truth，按漏检环节做消融，报告 recall、precision、成本和延迟。
